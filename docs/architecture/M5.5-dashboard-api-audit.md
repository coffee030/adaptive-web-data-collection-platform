# M5.5 Dashboard architecture and API audit

Baseline: the verified Windows launcher on which the M5.5 dashboard was developed.

| Feature | Existing component or API | Baseline | Minimal change |
| --- | --- | --- | --- |
| Dashboard shell | `App`, shared console CSS and feedback | Partial | Home Overview, five navigation destinations, semantic themes and responsive shell. |
| Recent jobs and records | `GET /collection-jobs`, `GET /records` | Partial | Add optional newest-first ordering. Display a bounded latest-jobs sample and bounded persisted Records. |
| Global totals | Jobs and Records return arrays without totals | Missing | Show explicitly scoped recent activity. Global totals are outside the implementation. |
| Guided eligibility | `GET /sources`, `GET /sources/{id}/versions` | Partial | Derive Topics from registered adapter-specific inputs. Filter approval and eligible versions using the full ProfileSnapshot DTO. |
| Submit and monitor | Existing creation form, request key, Job detail, events | Supported | Share submission and input validation. Use the existing Job monitor upon confirmation. |
| Data Explorer | `GET /records`, Record Details | Partial | Show persisted payload columns, bounded display preferences, and retain full structured inspection. |
| Job quality | Job DTO and `GET /collection-jobs/{id}/quarantine` | Supported | Present individual job counts and link to rejected entries. Duplicates are aggregate-only. |
| Evidence and provenance | Record DTO, Source, Profile Version, Job, Evidence Metadata | Supported | Keep lineage IDs and link to the existing details. Evidence exposes SHA-256 metadata. |
| External live HTML | `controlled_origin`, HTML web adapter | Blocked | The Core accepts literal loopback ports and the gated Compose fixture origin. The candidate has no documented authorization, permitted paths, or approved profile for a public target. |

## Newest-first lists

The current lists sort by `created_at, id` ascending. Reversing a single paginated response only shows the subset at its offset. Finding the newest rows from the frontend would require unbounded scanning because these routes do not report totals. Both lists accept optional `order=newest` with descending `created_at, id`; the default remains ascending and the existing status and job filters still apply. PostgreSQL can scan the existing composite indexes in reverse. The DTOs, limits, offsets and trusted-local boundary are unchanged. A regression test checks the default, stable ties, filtering, pagination and invalid order handling.

## Intentional limits

- Job and Record list pages keep the existing limit-plus-one pagination. The Overview recent activity summary uses only the latest five submitted Jobs, with no global totals.
- The Records API supports the `job_id` filter and has no `source_id` filter. The Explorer can select fields present on the current page. Global payload search and a global field catalogue would require new index and schema decisions and are not needed for this workflow.
- Quarantine exposes rejected candidates and validation reasons per Job. Duplicate counts come from the Job DTO. No duplicate candidate DTO, global quarantine query, or Evidence bytes route exists.
- Source/Profile lists have no pagination today. Topic discovery checks approved Sources in small batches, using the backend's immutable Profile snapshots. No domain categories can be inferred from the Source DTO. HTML pages and CSV datasets are the supported categories grounded in the configured adapters.
